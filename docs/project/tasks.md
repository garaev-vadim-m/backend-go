# Задачи на будущее

Приоритеты: **P0** — делать первым, **P1** — следующий этап, **P2** — после
основной функциональности. Зависимости указаны в каждом эпике.

Сводный порядок: **A и B (базовая аутентификация и роли — реализованы,
остались долги) → C (JWT) → E (корзина)**, затем F (качество и эксплуатация).
C и E можно менять местами.

---

## A. Базовая аутентификация (P0)

**Зависимости:** нет.
**Зачем:** ручки `POST /user/register`, `/user/login`, `/user/logout`,
`GET /user/me` и middleware работают; CRUD-роуты уже защищены ролью `admin`.
Здесь собраны оставшиеся долги по базовой аутентификации. Пути приведены к
текущим роутам (`/user/*`, а не `/auth/*`).

### A1. Расширить таблицу `users`

- [x] добавить `email VARCHAR(255)` (nullable, с уникальным ограничением из миграции 000009)
- [x] добавить `password VARCHAR(255)` (bcrypt-хеш, миграция 000006)
- [x] добавить `created_at`, `updated_at TIMESTAMPTZ` (миграции 000010/000011,
      значения по умолчанию `now()`; `updated_at` обновляется в `UPDATE`)
- [x] миграции применяются при старте через `golang-migrate`
      (`internal/database/migrations/`)

**Готово, когда:** схема применяется и на чистой, и на существующей БД.

### A2. Пароли

- [x] хеширование `golang.org/x/crypto/bcrypt` (`internal/auth`)
- [x] проверка пароля при логине; для старых пользователей остался fallback на
      открытый пароль через `subtle.ConstantTimeCompare`
- [x] минимальные требования к паролю: 8–72 байта
- [ ] перевести всех пользователей на bcrypt и убрать fallback

### A3. Эндпоинты

- [x] `POST /user/register` — регистрация (name, email, password), роль `user`
- [x] `POST /user/login` — вход, ответ `{"ok": true}` и `HttpOnly`-кука `session`
- [x] `POST /user/logout` — выход по куке `session`
- [x] `GET /user/me` — текущий пользователь (через `Auth.Require`: кука или
      `Bearer`; продлевает сессию)

**Готово, когда:** можно зарегистрироваться, войти, получить `/user/me` и выйти.

### A4. Сессии и куки

- [x] таблица `sessions` (id, user_id, token_hash, created_at, expires_at,
      revoked_at), хеш токена SHA-256, индексы по `user_id` и `expires_at`
- [x] TTL сессии при создании — 24 часа
- [x] `HttpOnly`, `SameSite=Lax`, `Secure` при `COOKIE_SECURE=true` — токен
      хранится в куке и передаётся браузером автоматически; фронтенд использует
      `credentials: "include"`
- [x] продление сессии (`Renew`, порог 12 ч) и фоновая очистка просроченных
      неотозванных записей старше 30 дней

### A5. Middleware

- [x] `Auth.Require`: читает сессию (кука или `Bearer`) через `session.Validate`,
      кладёт `Identity{ID, Role}` в `context.Context`
- [x] `IdentityFromContext(ctx)` helper
- [x] `401 Unauthorized` для защищённых маршрутов без валидной сессии

**Готово, когда:** защищённые ручки без входа дают `401`.

## B. Роли и права (P0)

**Зависимости:** A.
**Зачем:** создание/обновление/удаление доступно только админу. Роли хранятся в
таблице `rules` (`code`: `admin`, `user`); сервер проверяет их в
`Auth.RequireRole`; решение по GET зафиксировано: список пользователей — только
админу, справочники и товары — публично.

### B1. Роли

- [x] сидировать `rules`: `admin`, `user`
- [x] при регистрации назначать роль `user`
- [x] роль приходит из `session.Validate` вместе с id, лежит в `Identity.Role`
      и проверяется в `Auth.RequireRole` без дополнительного запроса

### B2. Middleware прав

- [x] `requireRole("admin")`
- [x] `401` — не аутентифицирован, `403` — аутентифицирован, но нет прав

### B3. Ограничить изменения

- [x] `POST` / `PUT` / `DELETE` для `users`, `status`, `rules`, `user_status`, `products` — только admin
- [x] `GET /users` — только admin; `GET /user?id=` и `GET /user/me` — авторизованным
- [x] справочники и товары (`GET /products`, `/statuses`, `/rules`, `/user-statuses`) — публичные
- [x] не-админ получает `404` на чужую карточку `/user?id=` (не `403`)

### B4. UI

- [x] в `admin_panel.html` скрывать/блокировать кнопки изменения для не-админа
- [x] для не-админа не загружать `/users` и блокировать карточки пользователей
- [x] `401` — `api()` очищает сессию и перенаправляет на `auth.html`; `403` —
      показывает ошибку прав без выхода из аккаунта

**Готово, когда:** обычный пользователь получает `403` на изменение, админ — выполняет.
Клиентская и серверная части готовы.

## E. Корзина, заказы и Redis (P1/P2)

**Зависимости:** A для корзины пользователя; анонимная корзина работает без auth.
**Идея (из плана):** временное хранение в Redis с id корзины, запись в БД после
паузы; любое действие с корзиной сбрасывает таймер (как debounce).
**Сейчас в бэке:** миграции 000013–000015, `POST /cart/items`,
`POST /order/checkout`; фронтенд эти ручки не использует.

### E1. Инфраструктура

- [ ] добавить `redis` в `docker-compose.yml` + volume
- [ ] клиент Redis (`github.com/redis/go-redis/v9`)
- [ ] env: `REDIS_ADDR`, `REDIS_PASSWORD`, `REDIS_DB`

### E2. Модель

- [x] таблицы `carts` (id, user_id, created_at, updated_at)
       и `cart_items` (cart_id, product_id, quantity) — миграция 000014
- [x] уникальность `cart_items (cart_id, product_id)`
- [x] `products.price` (000013) и `products.stock` (000015)
- [ ] раскрыть `price` и `stock` в моделях и API товаров: сейчас в
       `GET /products` / `GET /product?id=` их нет

### E3. API корзины

- [x] `GET /cart` — текущая корзина: `{"items":[{product_id,name,price,quantity,total}],"total"}`,
       только для авторизованных; пустая корзина отдаёт `items: []`
- [x] `POST /cart/items` — добавить товар: `{ "product_id": 1, "quantity": 2 }`,
       только для авторизованных, повтор добавляет quantity
- [ ] `PUT /cart/items` — изменить количество
- [ ] `DELETE /cart/items?product_id=` — удалить товар
- [ ] `DELETE /cart` — очистить

### E4. Временное хранение

- [ ] ключ `cart:<id>` в Redis, TTL (например, 30 мин)
- [ ] аноним: `cart_id` в куке (`HttpOnly`), при входе — merge в пользовательскую
- [ ] debounce: после последнего изменения запускать отложенную запись в БД
       (5–10 мин), таймер сбрасывается новым действием
- [ ] фоновая запись: горутина + `time.AfterFunc` или очередь; при рестарте
       не терять данные (описать поведение)
- [ ] при checkout или истечении TTL — финальная запись в БД

### E5. Оформление

- [x] `POST /order/checkout` — создать заказ из корзины; обязателен заголовок
       `Idempotency-Key` (до 64 символов), `201` при создании и `200` при повторе
- [x] таблицы `orders` / `order_items`, снимок цены в `order_items.price`,
       списание `products.stock`, очистка корзины в транзакции
- [ ] читать заказ по id/списком (`GET /order?id=`, `GET /orders`) — сейчас
       доступен только результат `POST /order/checkout`

### E6. Фронтенд корзины и оформления

- [ ] показывать `price` / `stock` в карточках товара и в форме админ-панели
- [x] кнопка «В корзину» в `index.html` с вызовом `POST /cart/items`
       и понятными ошибками (`401` → вход, `404` — товар не найден)
- [x] переход в корзину: ссылка в шапке витрины и страница `cart.html`
       с составом, ценами, количествами и итогом из `GET /cart`
- [ ] кнопка оформления: `POST /order/checkout` с `Idempotency-Key`,
       отображение `id` / `status` / `total`, обработка `400` (пустая корзина)
       и `409` (нет остатка)
- [ ] изменять состав корзины (количество, удаление, очистка): требует `PUT` и
       `DELETE` из E3 (бэкенд пока не реализован)

**Готово, когда:** аноним и пользователь могут собрать корзину, данные не теряются
при перезапуске приложения (в пределах TTL/после flush), корзина мержится при входе,
а витрина позволяет добавлять товары и оформлять заказ через API.
