# Задачи на будущее

Приоритеты: **P0** — делать первым, **P1** — следующий этап, **P2** — после
основной функциональности. Зависимости указаны в каждом эпике.

Сводный порядок: **A (auth base) → B (роли) → C (JWT) → D (OAuth) → E (корзина)**,
затем F (качество и эксплуатация). C и D можно менять местами.

---

## A. Базовая аутентификация (P0)

**Зависимости:** нет.
**Зачем:** сейчас API полностью открыт, а `users` не хранит учётные данные.

### A1. Расширить таблицу `users`

- [ ] добавить `email VARCHAR(255) NOT NULL UNIQUE`
- [ ] добавить `password_hash VARCHAR(255) NOT NULL`
- [ ] добавить `created_at`, `updated_at TIMESTAMPTZ`
- [ ] миграция `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (текущие миграции только создают таблицы)

**Готово, когда:** схема применяется и на чистой, и на существующей БД.

### A2. Пароли

- [ ] хеширование `golang.org/x/crypto/bcrypt`
- [ ] проверка пароля при логине
- [ ] минимальные требования к паролю (длина, не пустой)

### A3. Эндпоинты

- [ ] `POST /auth/register` — регистрация (email, password, name)
- [ ] `POST /auth/login` — вход, выдача сессии/токена
- [ ] `POST /auth/logout`
- [ ] `GET /auth/me` — текущий пользователь

**Готово, когда:** можно зарегистрироваться, войти, получить `/auth/me` и выйти.

### A4. Сессии и куки

- [ ] таблица `sessions` (id, user_id, expires_at) или подписанная кука
- [ ] `HttpOnly`, `SameSite`, `Secure` (в проде)
- [ ] TTL сессии и продление

### A5. Middleware

- [ ] `authMiddleware`: читает сессию, кладёт пользователя в `context.Context`
- [ ] `currentUser(r)` helper
- [ ] `401 Unauthorized` для защищённых маршрутов без сессии

**Готово, когда:** защищённые ручки без входа дают `401`.

Роли уже есть в таблице `rules` (`code`: `admin`, `user`).

### B1. Роли

- [ ] сидировать `rules`: `admin`, `user`
- [ ] при регистрации назначать роль `user`
- [ ] хранить роль в контексте запроса

### B2. Middleware прав

### B3. Ограничить изменения

- [ ] `POST` / `PUT` / `DELETE` для `users`, `status`, `rules`, `user_status`, `products` — только admin

**Готово, когда:** обычный пользователь получает `403` на изменение, админ — выполняет.

## C. JWT (P1)

**Зависимости:** A (B — опционально).
**Зачем:** токены для API/SPA без серверных сессий.

### C1. Токены

- [ ] access-token (короткий TTL, 15–30 мин)
- [ ] refresh-token (7–30 дней)
- [ ] claims: `sub`, `role`, `exp`, `iat`
- [ ] подпись HS256, секрет из env (`JWT_SECRET`)

### C2. Эндпоинты и middleware

- [ ] выдача токенов в `/auth/login`
- [ ] `POST /auth/refresh`
- [ ] `POST /auth/logout` (удаление/отзыв refresh)
- [ ] `jwtMiddleware` + `Authorization: Bearer <token>`
- [ ] `401` на истёкший или битый токен

### C3. Решение по сессиям

- [ ] выбрать: только JWT или JWT + серверный refresh
- [ ] описать выбор в `overview.md`

**Готово, когда:** API принимает Bearer-токен, refresh продлевает сессию.

## D. OAuth (P2)

**Зависимости:** A, желательно C.
**Зачем:** вход через внешнего провайдера.

### D1. Провайдер

- [ ] выбрать провайдера (Google/GitHub)
- [ ] зарегистрировать приложение, получить client id/secret
- [ ] env: `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET`, `OAUTH_REDIRECT_URL`

### D2. Flow

- [ ] `GET /auth/oauth/:provider` — редирект к провайдеру
- [ ] `GET /auth/oauth/:provider/callback` — обмен кода на профиль
- [ ] проверка `state` (CSRF)
- [ ] создать/найти пользователя по email
- [ ] связать несколько провайдеров с одним пользователем

### D3. Обработка конфликтов

- [ ] email уже занят локальным аккаунтом — что делать (связать/ошибка)
- [ ] роль для OAuth-пользователей

**Готово, когда:** вход через провайдера создаёт/находит пользователя и выдаёт сессию или токен.

## E. Корзина и Redis (P1/P2)

**Зависимости:** A для корзины пользователя; анонимная корзина работает без auth.
**Идея (из плана):** временное хранение в Redis с id корзины, запись в БД после
паузы; любое действие с корзиной сбрасывает таймер (как debounce).

### E1. Инфраструктура

- [ ] добавить `redis` в `docker-compose.yml` + volume
- [ ] клиент Redis (`github.com/redis/go-redis/v9`)
- [ ] env: `REDIS_ADDR`, `REDIS_PASSWORD`, `REDIS_DB`

### E2. Модель

- [ ] таблицы `carts` (id, user_id, created_at, updated_at)
      и `cart_items` (cart_id, product_id, quantity, price)
- [ ] уникальность `cart_items (cart_id, product_id)`

### E3. API корзины

- [ ] `GET /cart` — текущая корзина
- [ ] `POST /cart/items` — добавить товар
- [ ] `PUT /cart/items` — изменить количество
- [ ] `DELETE /cart/items?product_id=` — удалить товар
- [ ] `DELETE /cart` — очистить

### E4. Временное хранение

- [ ] ключ `cart:<id>` в Redis, TTL (например, 30 мин)
- [ ] аноним: `cart_id` в куке (`HttpOnly`), при входе — merge в пользовательскую
- [ ] debounce: после последнего изменения запускать отложенную запись в БД
      (5–10 мин), таймер сбрасывается новым действием
- [ ] фоновая запись: горутина + `time.AfterFunc` или очередь; при рестарте
      не терять данные (описать поведение)
- [ ] при checkout или истечении TTL — финальная запись в БД

### E5. Оформление (опционально)

- [ ] `POST /cart/checkout` — создать заказ из корзины
- [ ] таблицы `orders` / `order_items` (если нужно)

**Готово, когда:** аноним и пользователь могут собрать корзину, данные не теряются
при перезапуске приложения (в пределах TTL/после flush), корзина мержится при входе.
