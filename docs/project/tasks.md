# Задачи на будущее

Приоритеты: **P0** — делать первым, **P1** — следующий этап, **P2** — после
основной функциональности. Зависимости указаны в каждом эпике.

Сводный порядок: **A (auth base, частично сделано) → B (роли) → C (JWT) →
E (корзина)**, затем F (качество и эксплуатация). C и E можно менять местами.

---

## A. Базовая аутентификация (P0)

**Зависимости:** нет.
**Зачем:** ручки `POST /user/register`, `/user/login`, `/user/logout` уже
работают, но CRUD-роуты остаются открытыми, а проверка прав сделана только в
админ-панели. Пути в этом документе приведены к текущим роутам (`/user/*`, а не
`/auth/*`).

### A1. Расширить таблицу `users`

- [x] добавить `email VARCHAR(255)` (nullable, с уникальным ограничением из миграции 000009)
- [x] добавить `password VARCHAR(255)` (bcrypt-хеш, миграция 000006)
- [x] добавить `created_at`, `updated_at TIMESTAMPTZ` (миграции 000010/000011,
      значения по умолчанию `now()`; `updated_at` обновляется в `UPDATE`)
- [x] миграции применяются при старте через `golang-migrate`
      (`internal/database/migrations/`)

**Готово, когда:** схема применяется и на чистой, и на существующей БД.

### A2. Пароли

- [x] хеширование `golang.org/x/crypto/bcrypt` (`internal/auth`)
- [x] проверка пароля при логине; для старых пользователей остался fallback на
      открытый пароль через `subtle.ConstantTimeCompare`
- [x] минимальные требования к паролю: 8–72 байта
- [ ] перевести всех пользователей на bcrypt и убрать fallback

### A3. Эндпоинты

- [x] `POST /user/register` — регистрация (name, email, password), роль `user`
- [x] `POST /user/login` — вход, ответ `{"token": "..."}`
- [x] `POST /user/logout` — выход по `Authorization: Bearer <token>`
- [x] `GET /user/me` — текущий пользователь

**Готово, когда:** можно зарегистрироваться, войти, получить `/user/me` и выйти.

### A4. Сессии и куки

- [x] таблица `sessions` (id, user_id, token_hash, created_at, expires_at,
      revoked_at), хеш токена SHA-256, индекс по `user_id`
- [x] TTL сессии при создании — 24 часа
- [x] `HttpOnly`, `SameSite`, `Secure` (в проде) — сейчас токен лежит в
      `localStorage` и передаётся в заголовке `Authorization`
- [ ] TTL сессии и продление, очистка просроченных/отозванных записей

### A5. Middleware

- [ ] `authMiddleware`: читает сессию через `session.Validate`, кладёт
      пользователя в `context.Context`
- [ ] `currentUser(r)` helper
- [ ] `401 Unauthorized` для защищённых маршрутов без сессии (сейчас `401`
      возвращают только `/user/login` и `/user/logout`)

**Готово, когда:** защищённые ручки без входа дают `401`.

## B. Роли и права (P0)

**Зависимости:** A.
**Зачем:** создание/обновление/удаление должно быть доступно только админу.
Роли уже есть в таблице `rules` (`code`: `admin`, `user`), но сервер их не
проверяет.

### B1. Роли

- [x] сидировать `rules`: `admin`, `user`
- [x] при регистрации назначать роль `user`
- [ ] хранить роль в контексте запроса

### B2. Middleware прав

- [ ] `requireRole("admin")`
- [ ] `401` — не аутентифицирован, `403` — аутентифицирован, но нет прав

### B3. Ограничить изменения

- [ ] `POST` / `PUT` / `DELETE` для `users`, `status`, `rules`, `user_status`, `products` — только admin
- [ ] `GET` — доступен авторизованным (или публично, решить отдельно)

### B4. UI

- [x] в `admin_panel.html` скрывать/блокировать кнопки изменения для не-админа
- [x] обрабатывать `401` / `403`: общий обработчик `api()` показывает сообщение,
      очищает сессию и перенаправляет на `auth.html`

**Готово, когда:** обычный пользователь получает `403` на изменение, админ — выполняет.
Клиентская часть готова; серверные `403` появятся после B3.

## C. JWT (P1)

**Зависимости:** A (B — опционально).
**Зачем:** токены для API/SPA без серверных сессий.

### C1. Токены

- [ ] access-token (короткий TTL, 15–30 мин)
- [ ] refresh-token (7–30 дней)
- [ ] claims: `sub`, `role`, `exp`, `iat`
- [ ] подпись HS256, секрет из env (`JWT_SECRET`)

### C2. Эндпоинты и middleware

- [ ] выдача токенов в `/user/login`
- [ ] `POST /user/refresh`
- [ ] `POST /user/logout` (удаление/отзыв refresh)
- [ ] `jwtMiddleware` + `Authorization: Bearer <token>`
- [ ] `401` на истёкший или битый токен

### C3. Решение по сессиям

- [ ] выбрать: только JWT или JWT + серверный refresh
- [ ] описать выбор в `overview.md`

**Готово, когда:** API принимает Bearer-токен, refresh продлевает сессию.

## E. Корзина и Redis (P1/P2)

**Зависимости:** A для корзины пользователя; анонимная корзина работает без auth.
**Идея (из плана):** временное хранение в Redis с id корзины, запись в БД после
паузы; любое действие с корзиной сбрасывает таймер (как debounce).

### E1. Инфраструктура

- [ ] добавить `redis` в `docker-compose.yml` + volume
- [ ] клиент Redis (`github.com/redis/go-redis/v9`)
- [ ] env: `REDIS_ADDR`, `REDIS_PASSWORD`, `REDIS_DB`

### E2. Модель

- [ ] таблицы `carts` (id, user_id, created_at, updated_at)
      и `cart_items` (cart_id, product_id, quantity, price)
- [ ] уникальность `cart_items (cart_id, product_id)`

### E3. API корзины

- [ ] `GET /cart` — текущая корзина
- [ ] `POST /cart/items` — добавить товар
- [ ] `PUT /cart/items` — изменить количество
- [ ] `DELETE /cart/items?product_id=` — удалить товар
- [ ] `DELETE /cart` — очистить

### E4. Временное хранение

- [ ] ключ `cart:<id>` в Redis, TTL (например, 30 мин)
- [ ] аноним: `cart_id` в куке (`HttpOnly`), при входе — merge в пользовательскую
- [ ] debounce: после последнего изменения запускать отложенную запись в БД
      (5–10 мин), таймер сбрасывается новым действием
- [ ] фоновая запись: горутина + `time.AfterFunc` или очередь; при рестарте
      не терять данные (описать поведение)
- [ ] при checkout или истечении TTL — финальная запись в БД

### E5. Оформление (опционально)

- [ ] `POST /cart/checkout` — создать заказ из корзины
- [ ] таблицы `orders` / `order_items` (если нужно)

**Готово, когда:** аноним и пользователь могут собрать корзину, данные не теряются
при перезапуске приложения (в пределах TTL/после flush), корзина мержится при входе.
